GitHub 이슈 #$1 을 읽고, 브랜치를 따서 구현하고, 검증한 뒤 커밋까지 진행해줘.
PR 생성과 push 는 하지 말 것 — 내가 확인하고 직접 올린다.

## 1. 이슈 읽기

`gh issue view $1` 로 제목·본문·마일스톤을 확인한다.
`gh` 가 PATH 에 없으면 `& "C:\Program Files\GitHub CLI\gh.exe"` 로 호출한다.

이슈 본문의 **제안** 섹션이 있으면 그게 요구사항이다. 없으면 **문제** 섹션에서 직접 도출한다.

## 2. 브랜치 생성

**base 브랜치** — 이 레포는 마일스톤 브랜치로 PR 을 보낸다:

- 이슈에 마일스톤이 있고 같은 이름의 브랜치가 있으면 → 그 브랜치 (예: 마일스톤 `v1.0.2` → `v1.0.2`)
- 마일스톤이 없거나 같은 이름의 브랜치가 없으면 → `main`

`.github/workflows/auto-base-branch.yml` 이 PR 의 base 를 마일스톤 브랜치로 리타겟하므로,
로컬 브랜치도 같은 곳에서 따야 diff 에 남의 커밋이 섞이지 않는다.

base 브랜치로 checkout → `git pull --ff-only` → 거기서 새 브랜치를 딴다.

**브랜치 이름** — `<이슈번호>-<제목 슬러그>` (GitHub 이슈 브랜치와 동일한 형식):

- 공백은 `-`, `/` `?` `,` 같은 기호는 제거, 한글은 그대로 (예: `17-webgl-미지원렌더링-실패-시-에러-처리`)
- **번호 접두사는 필수** — CI 가 `^(\d+)-` 로 이슈를 찾아 base 리타겟과 이슈 자동 닫기를 한다

## 3. 구현

기존 코드 컨벤션을 그대로 따른다:

- 주석은 한국어. **왜** 이렇게 했는지를 적는다 (무엇을 하는지는 코드가 말한다)
- 주변 파일의 네이밍·구조·주석 밀도에 맞춘다. 새 스타일을 들여오지 않는다
- 이슈에 적힌 범위만 고친다. 지나가다 발견한 다른 문제는 고치지 말고 보고만 한다

## 4. 검증

```
npm run type-check
npm run lint
```

- lint 는 기존 경고가 여러 개 있다. **새로 늘어난 경고가 0** 이면 통과다
- 빌드 확인이 필요하면 `npm run build`. 단 이 명령은 부작용이 있다:
  - `src/assets/licenses.json` 을 재생성한다 → 줄바꿈만 바뀐 거면 `git checkout --` 로 되돌릴 것
  - Sentry 에 소스맵을 업로드한다 → 꼭 필요할 때만 돌릴 것
- 브라우저에서 눈으로 확인해야 하는 변경인데 확인하지 못했다면, **그 사실을 명시**할 것

## 5. 커밋

레포 컨벤션에 맞춘다 (`git log` 로 최근 스타일 확인):

- 제목: `feat:` / `fix:` / `ci:` / `chore:` + 한국어 요약
- 본문: 무엇이 왜 문제였는지 → 어떻게 고쳤는지. 판단이 필요했던 지점은 이유를 남긴다
- 마지막 줄에 `Closes #$1`

빌드 산출물(`dist/`)이나 재생성된 파일이 딸려 들어가지 않았는지 `git status` 로 확인하고 커밋한다.

## 6. 보고

작업 후 다음을 알려준다:

- 딴 브랜치 이름과 base
- 바꾼 파일과 핵심 판단 (특히 이슈에 안 적혀 있던 결정)
- 검증 결과, 그리고 **확인하지 못한 부분**
- 이슈 범위 중 하지 않은 게 있다면 무엇을 왜 뺐는지
